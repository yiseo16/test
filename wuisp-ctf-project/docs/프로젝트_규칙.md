# 통합 계약서

이 프로젝트에 참여하는 모든 조는 아래 항목을 반드시 지킵니다. 4조가 8/17~8/24에 전체를 하나로 합쳐야 하므로, 이 규칙들은 협의 대상이 아니라 고정값입니다.

## 1. 외부 포트

| 조 | 서비스 | 포트 |
|---|---|---|
| 1조 | SQLi | `8081` |
| 2조 | XSS | `8082` |
| 3조 | 파일 업로드 | `8083` |
| 4조 | 플랫폼 | `8080` |

## 2. 서비스명

각 조 `docker-compose.yml`의 웹 서비스 이름은 아래로 고정합니다. (DB나 봇처럼 내부용 서비스는 `sqli-db`, `xss-bot`처럼 접두어를 붙여 구분하세요.)

- `sqli-app`
- `xss-app`
- `upload-app`
- `platform`

## 3. `container_name`은 사용하지 않기

`container_name`을 지정하면 여러 조의 compose 파일을 한 번에 실행할 때 이름 충돌이 날 수 있습니다. 지정하지 말고 Docker Compose가 자동으로 이름을 붙이게 두세요.

## 4. 네트워크는 별도로 정의하지 않기

각 조 compose 파일에 최상위 `networks`를 직접 정의하지 마세요. 4조가 여러 파일을 `-f` 옵션으로 합쳐서 하나의 프로젝트로 실행하는데, 이때 모든 서비스가 자동으로 만들어지는 기본 네트워크를 함께 써야 서로 이름(`xss-app`, `xss-bot` 등)으로 통신할 수 있습니다.

## 5. 각 조 폴더에서 단독 실행이 되어야 함

자기 폴더로 들어가서 아래 명령만으로 정상 실행되어야 합니다.

```bash
docker compose up
docker compose down
```

## 6. 통합 명령과 담당자

전체 통합은 **4조**가 담당합니다. 저장소 루트의 `compose.yaml`이 각 조 Compose 파일을 include하므로, 루트에서 아래 명령만 사용합니다.

```bash
docker compose up --build
```

각 조의 단독 실행은 자기 폴더에서 `docker compose up`으로 확인합니다. `-f`로 여러 파일을 병합하는 방식은 상대 경로가 첫 번째 Compose 파일 기준으로 해석되므로 사용하지 않습니다.

## 7. README 형식

모든 조는 아래 순서로 README를 작성합니다.

```
1. 챌린지 설명
2. 실행 방법 (docker compose up)
3. 접속 주소
4. 의도된 풀이
5. FLAG 위치
```

## 8. 플래그 포맷

```
WUISP{설명적인_문자열}
```

예: `WUISP{sqli_login_bypass_success}`

## 9. 배포용 환경변수

- 실제 플래그와 `SECRET_KEY`는 Git에 올리지 않는 저장소 루트 `.env`에만 둡니다.
- 플랫폼의 `PUBLIC_HOST`는 로컬에서는 `localhost`, AWS에서는 EC2 공인 IP 또는 도메인입니다.
- `FLAG_XSS`와 XSS 봇의 `XSS_FLAG`는 반드시 같은 값으로 설정합니다.
